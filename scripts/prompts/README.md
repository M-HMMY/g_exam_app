# 章を書かせるときのプロンプト

教本の各章は、ここに置いたプロンプトを Codex CLI に渡して書かせます。**この内容は姉妹アプリ `itpassport_exam_app` で実際に効いたことの記録で、G検定向けに書き換えてあります。**

## 置いてあるもの

| ファイル | 用途 |
| --- | --- |
| `01-a-what.md` 〜 `12-l-ethics.md` | **章ごとの執筆プロンプト。12 章分そろっています** |
| [90-review.md](90-review.md) | 教本の通しレビュー（ひな形） |
| [91-review-questions.md](91-review-questions.md) | 確認問題の通しレビュー（ひな形） |

**番号は教本の並び順です。この順に書いてください。** 各プロンプトの「リンクしてよい節 ID」は、その章より前の章までしか列挙していないので、順番を飛ばすと存在しない節へのリンクが生まれます。

節割り（全 59 節の id とタイトル）は [docs/section-plan.md](../../docs/section-plan.md) にあります。**プロンプトと section-plan.md は同じ内容を持っているので、節割りを変えるときは両方を直してください。**

## 使い方

```bash
codex exec --cd "C:\Dev\g_exam_app" --sandbox workspace-write --color never \
  -o out.txt - < scripts/prompts/03-d-ml.md
```

- `--sandbox workspace-write` … このリポジトリの中だけ書き換えを許す
- `-o out.txt` … **最終メッセージだけ**をファイルに落とす。途中の思考ログを読まずに済むので、依頼した側のコンテキストを食わない
- `-` … プロンプトを標準入力から読む（長い日本語をシェルの引用符で壊さないため）

複数を同時に走らせられます。**ただし 1 ファイル 1 担当**にしてください。`src/data/textbook/<章 ID>.ts` と `src/data/questions/<章 ID>.ts` が 1 章 1 ファイルで対応しているのはこのためです。章 ID の一覧は `src/data/categories.ts` と `docs/syllabus-g2024.md` にあります。

## プロンプトに必ず入れること

実際に効いた要素です。省くと品質が落ちます。

1. **読むファイルの指定** … `CLAUDE.md`、`src/data/categories.ts` の該当章、**`docs/syllabus-g2024.md` の担当中項目**（目標とキーワードが、そのまま書くべき内容の外枠になります）、すでに完成した章（文体の見本）
2. **書くファイルの限定** … 「他のファイルは絶対に変更しないでください」。同時に走っている担当も明記する
3. **節の一覧を表で渡す** … id・タイトル・内容の目安。id を決めて渡さないと勝手な id を作ります
4. **読者像** … **G検定はここが姉妹アプリと違います。**「IT の基礎語彙はあるが、エンジニアではない」。「サーバ」「データベース」は説明なしで通じ、「勾配」「尤度」は通じない、と具体的に書くこと
5. **数式の扱いを明記する** … **出してよいが、解かせない・変形させない。**「読み方」を必ず添える（シグマが出たら「全部足す、という意味」）。入門編の「数式の読み方」（`i-3`）に依存してよいと伝える
6. **章の背骨** … その章を貫く一本の考え方（例：ブームの歴史なら「その時代は何を賢さだと考えていたか」、要素技術なら「予測する → 外れを測る → ずらす」）
7. **人名・モデル名の扱い** … 「それが何を変えたか」とセットで書かせる。名前の羅列を禁じる
8. **時点の明記を求める** … 生成 AI の記述には「いつ時点の話か」を本文に書かせる。**このアプリ固有の要求です**
9. **節の骨格** … ざっくり言うと → 本論 → まとめ → quiz。digest.ts が拾う書式なので崩されると困ると明記する。**` ```quiz ` は 1 節 5 問以上**（本番は 1 問 約 41 秒で、一問一答が速度対策そのものになる）
10. **記法の注意** … バックスラッシュのエスケープ、ヒアドキュメント禁止、`compare` は偶数個、図の中で `**` は効かない。**数式が多いこのアプリでは、バックスラッシュ落ちが姉妹アプリより起きやすい**
11. **リンクしてよい節 id の全列挙** … これを省くと存在しない節へリンクして検査に落ちます
12. **間違えやすい事実の名指し** … 「適合率は TP/(TP+FP)、再現率は TP/(TP+FN)」「Q 学習は方策オフ型、SARSA は方策オン型」「L1 がスパース」のように、誤りやすい箇所を先回りで釘刺しする。**姉妹アプリでは実際にこれが効いて、名指しした箇所は全章で正しく書けていました。**名指しの候補は [90-review.md](90-review.md) の「特に間違いが多い箇所」に並べてあります
13. **`npm run check` は実行させない** … 並行実行だとキャッシュが衝突するため。検査は依頼した側がまとめて 1 回やる

## 通しレビューのひな形

書いたものを検証させるプロンプトは [90-review.md](90-review.md) にあります。書くときとは要点が違います。

- **`--sandbox read-only` で走らせる。** レビューには指摘だけさせて、直すのは依頼した側。書き換えまで任せると、何が変わったのか追えなくなります
- **「自信がない箇所はありませんでした」を先回りで禁じる。** これを書かないと、毎回その報告が返ってきます。「確信度: 低」でもいいから必ず挙げさせること
- **間違いが多い箇所を名指しする。** 実際に効きました。G検定では、評価指標の分子分母、方策オン／オフ、L1 と L2、GAN の生成器と識別器、法律の年数と条番号、そして**記述がいつ時点のものか**
- **問題をレビューさせるときは [91-review-questions.md](91-review-questions.md) を使う。** 教本用の 90 番とは見る点が違います。教本は「書いてあることが正しいか」ですが、問題は**「正解が本当に 1 つに定まるか」**が最大の論点です。誤答が実は正しい、前提条件が書かれていない、といった型は、問題を対象にしないと出てきません
- **1 ジョブ 40〜80 問に割る。** 1 問ずつ 4 択すべてを判定させるので、教本より小さく割らないと雑になります。姉妹アプリでは 334 問を 6 ジョブに分けて 94 件出ました
- **範囲外のことまで指摘してくる。** 姉妹アプリでは、プロンプトで例示した語につられて、試験範囲外の項目を「重大な欠落」として報告してきました。**こちらの例示がそのまま誘導になります。**G検定では `docs/syllabus-g2024.md` に対応キーワードがあるかで範囲の内外を判定できるので、レビュー側にもそれを読ませたうえで、採否は依頼した側が判断すること

直させるときは、**指摘をそのまま渡さず、採否を判断してから渡します。**「直す」「直さない（理由）」を分けて書いた指示にすると、余計な書き換えが減ります。

## Codex の利用上限に注意

5 本を並行で走らせたとき、3 本が**編集を終えた直後・報告を書く前**に利用上限に当たりました。ファイルは書き換わっているのに `-o` の出力が空、という状態になります。

- **`-o` の出力が空でも、ファイルは変わっていることがある。** `git diff` で必ず確かめる
- **何が済んで何が残ったかは、こちらで検算する。** 指示した用語を `grep -c` で数えるのが速いです
- 残りは自分で直せる分量のことが多いので、上限の回復を待つより手で埋めた方が早い場合があります

## 報告を鵜呑みにしないこと

Codex は毎回「事実に自信がない箇所はありません」と報告してきますが、**そのまま信用してはいけません。** 姉妹アプリでは、動作確認で章数を 15 → 12 と取り違えた例があります。

- 機械的な検査は `npm run check` で必ず確認する
- 内容の正しさは、**書いた人とは別の目**で通しレビューする（この方針の根拠は CLAUDE.md に書いてあります）
